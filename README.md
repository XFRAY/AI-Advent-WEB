# День 15: Контролируемые переходы состояний

Ассистент хранит жизненный цикл задачи отдельно от диалога, профиля, памяти и инвариантов. Переходы проверяются детерминированно до вызова модели, поэтому этап нельзя пропустить формулировкой в чате.

## Жизненный цикл

```text
planning --approve_plan--> implementation --validation--> validation --finalize--> done
     ^                         ^                              |
     |                         +-----------rework--------------+
     +--replan-- (из implementation)
```

- `planning -> implementation` разрешён только после сохранения ответа с планом и команды «Утверждаю план».
- `implementation -> validation` требует хотя бы один сохранённый результат реализации.
- `validation -> done` требует хотя бы один сохранённый результат проверки.
- `validation -> implementation` («Доработать» или «Доработать: что именно исправить») возвращает задачу на доработку. Модель сразу вызывается: она получает замечания из последней проверки и ваш текст после команды и исправляет реализацию в рамках утверждённого плана; ответ сохраняется как новый результат реализации. Результаты проверки очищаются, поэтому финал требует новой проверки.
- `implementation -> planning` («Пересмотреть план») нужен, чтобы изменить утверждённый план: результаты реализации и проверки очищаются, план возвращается на пересмотр и требует нового утверждения. Пока план не обновлён, «Утверждаю план» блокируется.
- `reset` начинает новый цикл с `planning` и очищает артефакты этапов.

Текущий этап сохраняется в SQLite после каждого перехода. После перерыва, перезапуска сервера или возвращения пользователя приложение загружает сохранённый этап и продолжает с него.

Утверждённый план передаётся модели в промпте этапа как источник истины (`Approved plan`). Запрос, который меняет или расширяет то, что зафиксировано в плане, модель не выполняет: она предлагает «Пересмотреть план». Это защита на уровне промпта, а не жёсткая блокировка на сервере.

Чистые команды перехода обрабатываются без модели и сохраняются в истории как детерминированные ответы ассистента.

Поддерживаются четыре явные группы:

- `architecture` — выбранная архитектура;
- `technicalDecisions` — принятые технические решения;
- `stackConstraints` — ограничения по стеку;
- `businessRules` — бизнес-правила.

Каждая строка поля считается отдельным активным правилом. Формулировки `Не использовать ...`, `Запрещено: ...`, `Использовать только ...` и их английские аналоги участвуют в deterministic conflict guard. Если запрос явно требует нарушить такое правило, API возвращает `409` и не вызывает модель.

Изначально инварианты пусты: набор правил по умолчанию не создаётся ни при первом запуске, ни после очистки. Задайте их в UI или через `PUT /api/invariants`.

## Порядок проверок и контекста

Для `POST /api/chat`: сначала проверяются инварианты Day 14, затем lifecycle Day 15, и только потом вызывается модель.

1. Базовая system-инструкция агента.
2. Обязательные инварианты.
3. Текущий lifecycle.
4. Активный профиль пользователя.
5. Long-term memory.
6. Working memory.
7. Short-term dialogue.
8. Текущий запрос.

Инварианты не извлекаются из диалога автоматически. Они редактируются только явно через UI или API.

## API

- `GET /api/task-lifecycle` — текущий этап, артефакты и доступные намерения.
- `GET /api/invariants` — текущие инварианты и число активных правил.
- `PUT /api/invariants` — полная замена текущего набора инвариантов.
- `DELETE /api/invariants` — очистка инвариантов.
- `POST /api/chat` — проверка инвариантов и lifecycle, сборка контекста и запрос к модели.
- `DELETE /api/memory` — очистка диалога и working/long-term memory, сброс lifecycle в `planning`; профили и инварианты сохраняются.

Запрещённый переход возвращает `409 LIFECYCLE_TRANSITION_BLOCKED` и не вызывает модель.

Пример конфликта:

```text
Инвариант: Не использовать Python
Запрос: Используй Python для нового сервиса
Ответ: Не могу предложить это решение, потому что оно нарушает инвариант: Не использовать Python
```

### Сценарии ручной проверки

Регулярные выражения блокируют только императивные команды («Начни реализацию», «Переходи сразу в done»). Обсуждение этапов в тексте («Составь план реализации», «Проверь план на полноту») блокировкой не считается и обрабатывается моделью в рамках текущего этапа.

Модель завершает план секцией «Открытые вопросы:» (список или «нет»). Пока там есть вопросы, утвердить план нельзя.

1. **Недопустимые переходы.** На этапе `planning` отправьте «Начни реализацию», затем «Переходи сразу в done». Ожидание: предупреждение «Запрос отклонён», этап остаётся `planning`, вызова модели нет (`409 LIFECYCLE_TRANSITION_BLOCKED`).
2. **Допустимый путь.** «Составь план реализации …» → «Утверждаю план» → «Реализуй план» → «Проверь реализацию» → «Финализируй задачу». Финал без проверки и проверка без реализации блокируются. «Доработать» (можно с уточнением: «Доработать: добавь проверку пустого ввода») на этапе `validation` возвращает в `implementation` и сразу запускает исправление; затем снова «Проверь реализацию».
3. **Продолжение после паузы.** На любом этапе перезапустите сервер и обновите страницу: степпер и доступные действия восстанавливаются из SQLite, следующий разрешённый шаг работает, а «перепрыгнуть» его по-прежнему нельзя.
